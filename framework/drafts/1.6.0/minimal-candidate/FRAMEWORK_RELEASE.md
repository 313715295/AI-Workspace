# Framework release governance

## 1. Version classes

- `PATCH_HOTFIX`: compatible narrow correction; no new public topology.
- `MINOR`: compatible capability or project-control contract with migration.
- `MAJOR`: incompatible project/task/authority topology.

Framework 1.6.0 is a MINOR release from immutable 1.5.2. The draft, implementation candidate, integration candidate, stable version, live root replacement, CURRENT selection, and every project pin are separate objects and actions.

## 2. 1.6.0 release gates

1. exact candidate inventory, strict UTF-8/LF, JSON and PowerShell syntax;
2. loader topology and byte-cost caps, with no new A-C+G module;
3. authorization positive/negative cases including current controller epoch;
4. routine exclusions remain structural project data; each bounded consumer validates literal paths at use, applies default exclusion or an exact-path override, and returns `UNVERIFIED` rather than broadening a failed operation;
5. isolated real-Git registration and four-source serial migration, interrupted-upgrade recovery with retained material, repeat health, routine-exclusion output/action negatives, and STATUS/DIFF/INDEX command-failure honesty;
6. old-tree zero effective imports/calls, stable 1.5.2 and live root zero drift;
7. fresh independent CRITICAL Review of the frozen candidate;
8. knowledge work, integration and final release only through their separate current task gates.

Tests prove only their actual isolated/static boundaries. A checker without a real invocation consumer is not a delivered capability. A draft PASS is not release, real remote execution, CURRENT selection, Pocket pin adoption, or project knowledge initialization.

## 3. Publication order

Freeze candidate and manifest, obtain independent Review, implement and review the separately gated knowledge capability when its evidence prerequisites are met, integrate the approved ranges, run final release verification, create the immutable stable version, then separately decide live root replacement and CURRENT. Existing projects opt in through their own migration task; none is upgraded automatically.

Stable versions are never edited in place. A later correction creates a new version.
