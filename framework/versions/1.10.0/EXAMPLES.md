# Framework 1.10.0 examples

## Explicit new-project selection

A user selects Framework 1.10.0. Registration preview validates the sealed release and exact starter. Apply materializes the starter and project-owned pin. No root default or consumer record is created.

## Existing-project upgrade

A project task freezes its schema3 control plane, Controller and custom region, previews `ToVersion=1.10.0`, then applies only managed project/Bootstrap objects. A fresh cold recovery proves the new pin. Framework stores no adoption entry.

## Same-scope new task

A user approves a Framework upgrade outcome. Routing determines a separate release task is `MUST_NEW`, while project, owner, resource and protection boundaries are unchanged. Standing create authority allows the task without another confirmation. A request to add push or device work is `BLOCKED` and returns to the user.

## Terminal delivery

An executor completes the authorized candidate and sends one compact `READY` report directly to the task owner or already-selected independent Reviewer. It routes to Controller only when Controller owns the unique next action or an explicit escalation boundary exists. It does not wait for ACK. If the host cannot authenticate or deliver the route, it returns `REPORT_CHANNEL_UNAVAILABLE`.

## Batch authorization

One package grants `SOURCE_WRITE`, `TEST_WRITE` and `TEST_RUN`. The checker receives the requested action array once and emits one PASS/FAIL result per action. A write-induced identity drift ends that lease for later phases; Review and Git still require separate packages.

## Evidence ceiling

Anonymous fixtures prove generic preservation and failure behavior. They do not prove natural host quality, savings or adoption in a real project.
