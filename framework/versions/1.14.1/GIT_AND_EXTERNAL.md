# Git and external actions

Git evidence is repository-specific. Use the versioned protected safe-Git helper, exact safe.directory configuration and explicit Git top. Never combine Maintenance, Framework target or consumer state into one status claim.

`GIT_STAGE`, `GIT_COMMIT`, `PUSH` and `EXTERNAL` are separate actions. Use exact paths; never substitute `git add .`. A source or Review package grants none of them.

Before staging, reprove candidate identities, index state, unrelated dirty paths and Review disposition. After commit, report commit and parent identities plus protected-safe status/index. Push requires remote and branch authority and fresh remote evidence.

A Framework release and a project's explicit upgrade are independent. Framework Git publication does not discover or modify consumers.

No background publication, retry/compensation, account action or external claim is implied by local PASS.

## Bounded Domain Owner external route

A current DOMAIN_OWNER may directly issue one pure `EXTERNAL` package for one user-approved, free, domain-local atomic batch. The package binds provider, ordered operations, exact payload identities and canonicalization, quantity/retry ceilings, output use, stop conditions and a non-reissuable ambiguous-consumption stop. `ZERO_PROJECT_DATA` is a closed class limited to provider public-metadata reads, public-status reads and capability discovery; any other operation must bind exact payloads.

The direct route is unavailable when payment/subscription, commercial licensing, account or credential change, public publication, installation, protected/secret upload, cross-domain impact, formal asset activation, project-phase change, Git/PUSH, shared quota/resource or unknown scope is present. Any such flag routes to PROJECT_CONTROLLER; changing a result kind does not make this rule disappear. The action checker, process resolver and actual host capability remain independent gates.
