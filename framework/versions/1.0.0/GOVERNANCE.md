# 多会话协作治理 v1.0.0

## 1. 目标与基本原则

这套框架用于“一个主控、三个专业分管、若干执行会话”的项目协作。会话数量由真实并行需求决定，不为组织图而创建空会话。

共同原则：

1. 项目权威文档和已验证代码是事实来源，聊天记录不是。
2. 一项任务只有一个写入负责人、一个明确审核人和一组明确文件所有权。
3. 先建立证据与影响范围，再设计、实现和验证；优先修根因，不用局部补丁掩盖系统问题。
4. 方案、实现、审核形成可追踪闭环；“测试通过”不等于“设计正确”或“新增行为已覆盖”。
5. 不覆盖、回退、暂存其他会话或用户的并行改动。
6. 面向用户的结论使用简体中文；代码标识与必要术语可保留英文。

## 2. 角色与权限

| 角色 | 默认资源 | 负责 | 可以批准 | 不负责 |
|---|---|---|---|---|
| 主控 | R3 战略级 | 项目目标、跨域取舍、阶段门、任务路由、冲突仲裁、全局状态 | 跨域变更、阶段切换、路线变化、分管争议 | 日常替分管逐文件审核、长期承担执行 |
| 美术/渲染分管 | R3 战略级 | 视觉方向、资产规范、渲染表现与性能、该域任务拆分和验收 | 本域常规方案与实现 | 游戏规则或核心架构的最终决定 |
| 架构/核心逻辑分管 | R3 战略级 | 架构边界、模拟核心、AI/规则/数据流、测试策略、该域验收 | 本域常规方案与实现 | 产品体验目标的单方面重定义 |
| 游戏设计分管 | R3 战略级 | 核心体验、机制契约、数值意图、关卡/商业化/可读性、设计验收 | 本域常规方案与文档 | 越过架构分管直接指定危险实现细节 |
| 执行会话 | R1 执行级，必要时 R2 | 按任务卡调查、实现、验证、交接 | 不批准自己的产出 | 扩大范围、改变路线、同时扮演最终审核人 |

R1/R2/R3 是能力等级而非固定模型名：R1 适合边界明确的实现与检索；R2 适合中等复杂度设计/调试；R3 适合分管和主控的长上下文、跨文件与高风险判断。具体模型和推理等级由用户选择。

### 2.1 谁作最终决定

- 本域、可逆、无跨域契约变化的常规任务：分管审核通过即可合入，主控只接收状态摘要。
- 跨两个及以上领域、改变项目路线/阶段门/公共契约、风险不可逆或分管有争议：主控决定。
- 目标、商业取舍、重大删改、发布/外部行为等需用户授权的事项：主控整理选项与证据，用户决定。
- 审核不是永久独立部门。高风险、争议或长期上下文污染时，创建一次性独立审核会话；否则分管承担审核。

## 3. 任务生命周期

```text
BACKLOG → READY → IN_PROGRESS → REVIEW → APPROVED → MERGED → VERIFIED → CLOSED
                           ↘ CHANGES_REQUESTED ↗
任意进行中状态 → BLOCKED / CANCELLED
```

每张任务卡至少包含：目标、非目标、权威输入、文件所有权、风险等级、负责人、审核人、验收与验证、交接产物。状态变化必须写入任务卡；项目级变化再同步 `STATUS.md`。

执行会话开始时必须先回报：角色、任务 ID、已读资料、工作树风险、计划与预计写入范围。发现超出任务卡的必要工作时先记录影响并升级，不悄悄扩大范围。

## 4. 风险与审核

- 轻：局部、可逆、无公共契约或持久状态变化。分管可采用精简审核。
- 中：跨多个文件/模块、改变行为或新增状态。必须做影响分析、专项测试和分管完整审核。
- 重：跨域、公共契约、持久化/生命周期、核心循环、发布或不可逆改动。先评审方案；分管审核后还需主控阶段门，必要时独立盲审。

独立审核的触发条件：作者与审核人上下文高度重合且判断风险高；同类问题连续两次复发；跨域分歧；核心架构/数据迁移/发布门；用户或主控明确要求。独立审核会话只做指定维度，不自动获得写入权。

## 5. Git 与并行写入

共享本地仓库默认不为每个会话创建分支或独立 index。这样能降低切换与合并成本，但必须遵守：

1. 任务卡列出精确文件所有权；不同执行会话不得同时写同一文件。
2. 同一代码仓库同一时刻只允许一个“Git 收口者”执行暂存/提交。
3. 收口前检查 `HEAD`、`git status`、目标差异；只暂存任务拥有的精确路径，禁止在脏工作树使用 `git add .`。
4. 审核由分管批准；提交可由分管或其指定执行会话完成。提交不代表主控审批。
5. push、发布、删除、回退等另行授权；不得用 `assume-unchanged` 或 `skip-worktree` 隐藏差异。

仅在以下情况使用独立 branch/worktree：文件所有权不可避免重叠；长周期实验需要隔离；两个候选方案并行；变更必须保持主工作树可发布。使用前由分管指定集成负责人和合并顺序。

## 6. 会话交接、恢复与关闭

- 会话接近上下文极限、长期停顿或换模型时，更新任务卡：已完成、证据、未完成、当前差异、验证结果、下一步、风险。
- 新会话只从项目 Bootstrap、状态和任务卡恢复，不依赖旧聊天摘要猜测。
- 被替换会话停止写入；有价值的稳定结论迁入项目文件，无价值的过程讨论直接结束。
- 老项目首次接入时可做一次性迁移并保留原始只读归档；迁移不是日常工作流，新项目不创建“旧会话迁移”任务。

## 7. 质量纪律

- 使用搜索和结构检查建立注意力地图，再阅读相关原文。
- 设计前做简短 pre-mortem：最可能失败的三件事及防线。
- 公共概念必须有单一权威来源；摘要只给指针，不复制会漂移的详细规则。
- 新模块/新行为要有直接覆盖；既有回归全绿只证明旧合同未明显破坏。
- 功能或契约改变时同步受影响的权威文档、开发日志和任务状态，不进行无关“全面同步”。
- 正式文档不引用临时聊天编号或临时方案作为权威依据。
