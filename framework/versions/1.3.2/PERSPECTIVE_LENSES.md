# 评审视角库 v1.3.2

## 1. 为什么使用“视角”而不是“固定专家人格”

旧流程把十二位人物绑定到十二个维度。它提醒了很多重要问题，但人物名称本身不会产生独立性：同一个模型在同一上下文中模拟十二个角色，证据来源、注意力和偏差仍高度相关，还可能制造未经核实的引语或诉诸权威。

因此保留其方法，改为可复核的问题视角：

- 不模拟人物口吻，不声称代表真实人物。
- 不凭名字给结论，每项必须引用项目事实、权威文档、代码、测试或测量。
- 不要求每次全选；任务卡按风险选取。
- 需要真正独立判断时使用新审核会话，而不是在同一会话切换角色名。
- 可以注明思想来源帮助理解，但不得编造或无来源引用原话。

## 2. 十三个可选视角

| 视角 | 历史来源提示 | 核心问题 |
|---|---|---|
| AI 能力边界 | Karpathy 等 AI 工程实践 | 模型/自动化在哪些输入下可靠？失败如何检测和降级？ |
| 程序理论与有机修改 | Naur | 修改者是否理解“为什么”？新内容是否融入既有理论？ |
| 模块深度与接口复杂度 | Ousterhout | 接口是否隐藏复杂度？模块是否过浅、泄漏实现？ |
| 游戏引擎边界 | Gregory | Core/Render、平台、帧循环、资源生命周期是否正确分离？ |
| 认知偏差与决策 | Kahneman | 是否受确认偏差、沉没成本、可得性或锚定影响？ |
| 测试与安全重构 | Feathers | 是否有 seam、安全网、直接覆盖和可回归合同？ |
| 数据导向性能 | Acton 等数据导向实践 | 热路径分配、缓存局部性、批处理和测量是否合理？ |
| 游戏体验与可学习性 | Koster 等游戏设计理论 | 玩家能否读懂因果、学习规则并获得有意义选择？ |
| 领域语言与模型 | Evans | 术语是否统一？模型是否表达领域而非技术偶然？ |
| 依赖方向与职责边界 | Clean Architecture 等 | 高层策略是否依赖细节？职责和状态所有者是否唯一？ |
| 战略原则 | 项目采用的兵法/战略资料 | 机制“为什么这样打”是否符合项目设计原则？ |
| 战术执行与战场判断 | 项目采用的战史/战术资料 | 感知、判断、命令和执行链是否可用且不泄露信息？ |
| 平台与发行生命周期 | 平台工程与发布工程实践 | 工具链、SDK/runtime、账号/AppID、构建产物、测试版本、生命周期与正式发布是否有明确所有权、证据和失败恢复？ |

这些“来源提示”不是权威替代。项目设计原则和可复核证据始终优先。

## 3. 选择规则

- `MICRO`：默认不选，除非当轮有一个明确的特定风险。
- `STANDARD`：按风险选择最相关的0–3个视角；普通局部工作可不选并说明直接验证足够。
- `CRITICAL`：选择3–5个视角，并说明为何未选其他视角。
- 不默认十二项全上；若确需全景评估，应拆成互不重复的检查维度并汇总证据。

常见组合：

- 核心架构：程序理论、模块深度、依赖方向、测试、性能。
- 渲染与资产管线：引擎边界、性能、游戏体验、认知偏差。
- 游戏机制：游戏体验、领域语言、战略原则、战术执行。
- AI 决策：AI 能力边界、领域语言、认知偏差、战术执行、测试。
- 平台/发行：平台与发行生命周期、游戏引擎边界、依赖方向、测试与安全重构、认知偏差。

## 4. 输出格式

每个被选视角输出：

```text
视角：<名称>
结论：通过 / 有问题 / 不适用
证据：<文件、代码、测试、运行测量或权威章节>
问题：<具体偏差；无则写“未发现”>
阻塞性：阻塞 / 非阻塞
建议：<最小且可验证的下一步>
```

“优化建议”不能掩盖实际阻塞问题；“通过”必须说明检查了什么。评审视角只提供审核证据，最终批准权仍按 `GOVERNANCE.md`。
