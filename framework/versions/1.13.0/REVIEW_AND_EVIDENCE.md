# Review and evidence

## Risk follows action

Independent Review is required for public contract changes, candidate payload, Controller/long-lived owner switch, Git integration with material scope and external action where the profile requires it.

Mechanical formatting, canonical projection and release-field sealing may use direct checker evidence when they do not change the already reviewed public contract or candidate payload.

Review never grants write, Git, push or external capability.

For an unchanged domain task, the DOMAIN_OWNER may directly select the independent Reviewer and issue the pure `REVIEW_EXECUTE` package. PROJECT_CONTROLLER is not a mandatory signing or delivery hop. In CRITICAL scope the task owner, issuer, candidate writer and material solution contributors are mechanically disqualified; a qualified cross-domain writer remains a writer/contributor and does not change task ownership. `OWNER_ACCEPT` is a later domain/product gate, not Review.

## Candidate freeze

A stable candidate identifies repository, parent/baseline, exact files, byte identities, canonical payload, known dirty/index state, writer release and evidence ceiling. Canonical immutable evidence is stored once and referenced; do not duplicate it across mutable cards or add a field-level manifest.

A finding does not authorize repair. Same-scope repair receives a fresh writer package, updates the affected freeze and receives fresh Review of the changed candidate.

When a release declares a project correction incorporated, Review evaluates the original correction reason, effective rule and applicability boundary against the actual normative modules and behavior tests. A coverage ID, changelog statement or approximately similar prose is not acceptance evidence by itself.

## 1.13.0 release sequence

1. one implementation writer completes source and direct/immutable-1.12 regression tests;
2. project final `VERSION.json` lifecycle fields and freeze the exact release payload;
3. writer releases;
4. the current task owner routes the exact candidate directly to a fresh independent CRITICAL Reviewer under a pure `REVIEW_EXECUTE` package;
5. Maintenance OWNER_ACCEPT records the task owner's separate acceptance of the exact approved payload;
6. the owner-accepted candidate receives only the excluded release-manifest seal and reviewed root integration projection;
7. focused verification confirms every reviewed payload byte is unchanged;
8. Git stage/commit and push remain separate later packages.

## Evidence ceilings

Direct fixtures can prove generic contracts, failure cases, canonical manifests and anonymous project preservation. Optional post-release project observations can expose actual invocation, false-block/leak and cost evidence for the originating project, but they do not block release or prove universal semantic correctness, model attention, browser/device state, remote publication or external claims.

The official PowerShell 7 backend must preserve timestamp strings and normalized results on every claimed platform. 1.13.0 claims Windows only. Any later Linux or macOS claim requires its own actual conformance result; a missing platform/runtime is an explicit evidence ceiling, not a fabricated pass.
