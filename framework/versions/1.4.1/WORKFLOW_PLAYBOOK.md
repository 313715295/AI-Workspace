# 工作流程手册 v1.4.1

本手册回答“怎么工作”；`REVIEW_CHECKLIST.md` 回答“怎么审核”。项目和任务卡可以提高要求，不能静默降低框架要求。

## 0. 唯一端到端流程

长期责任只有主控与领域分管两层；执行者和独立审核者按任务临时挂载。每张任务只有一个长期owner，该owner同时是唯一调度者。完整路径只有这一条：

1. **接收与路由**：主控判断主领域、跨域关系和阶段顺序。纯领域问题交分管直接调查和讨论；跨域目标默认指定一个主owner和一张父卡，不建立双owner，也不按领域数量机械拆包。只有独立生命周期/owner字节/外部状态/可关闭交付物/必须保留的审核结论才建子卡，并绑定父卡consumer与退出条件。
2. **一次授权**：主控只冻结目标、阶段/公共边界、owner、禁止事项、外部/Git权限和升级条件，不替分管写日常方案与pathset。领域owner在边界内不逐项向主控申请。
3. **任务建制**：owner先选择最低充分档位。`MICRO`同turn明确目标、exact/forbidden、验证、Git/外部权限和结果，可不建卡；`STANDARD`使用紧凑卡；`CRITICAL`才核对完整producer、direct consumer、tests、runner/manifest、docs、contingency closure、行为不变量、审核人、证据门和回传对象。所有档位先冻结真实范围和权限；范围不完整时只调查不写入。有持久卡时使用对应`范围摘要`，进入Review前由AI把机器观察actual传给固定版本checker。
4. **执行与复审**：`MICRO`由健康owner同turn实施、自检并落结果；无独立触发条件的`STANDARD`可由领域owner实施并聚焦审核，也可按风险使用另一个合格上下文；`CRITICAL`由执行者在冻结范围内实施、自检并交接，owner冻结candidate manifest、稳定内容对象/section identity、依赖manifest和验证上限，再闭合红灯、返工和Review轮次。宿主消息扩展只在实际需要时启用。实质写入者不得冒充所需独立批准；公共合同、持久状态、核心循环、跨域状态机或重大玩家体验变化的最终审核人必须与方案设计者及实质写入者不同。
5. **提交与回报**：任务卡已预授权本地Git时，审核通过后由指定closer把机器观察actual逐卡传入检查器，再逐项stage、检查cached对象、正常hook提交，并复核commit tree、parent、index、非任务边界和最窄post-commit smoke。push、发布与外部状态始终另门；内容提交后仍有外部发布的同一卡保持active，外部成功并落账后才用closure提交归档。领域owner只向主控发送一次阶段所需摘要。
6. **阶段收口**：主控只核对稳定对象、跨域/阶段影响、所有权释放和下一阶段，不重复领域完整审核或重跑同一有效键。
7. **关闭与恢复**：owner只关闭并归档所有授权动作和外部结果都已真实完成的任务；外部发布阻断时原卡保持active并记录真实状态。被父卡消费的临时领域包立即退出热入口。正式权威存稳定合同，任务卡存过程与证据，项目状态存current。工作上下文释放旧权限后按复用条件保留或退出当前热工作集；首次进入或基线不可证明时做`FULL_COLD_RECOVERY`，同一健康上下文且基线可证明时按`WARM_TASK_REBIND`增量重绑，不依赖聊天摘要或继承旧权限。

默认决定边界：

| 事项 | 默认决定者 | 是否升级主控 |
|---|---|---|
| 本域私有实现、算法/样本校正、exact或已列contingency内返工 | 领域分管 | 否 |
| 已冻结任务的执行资源、测试组合、Review轮次、预授权本地Git | 任务owner | 否 |
| 单领域玩家可见复杂行为 | 分管直接与用户确认并持久化 | 仅改变阶段/公共合同/owner时 |
| 新公共接口/持久状态、跨域合同、所有权冲突或明显风险升级 | 主控 | 是 |
| 路线、阶段优先级、质量底线、重大产品取舍 | 主控整理；需用户权限的部分由用户决定 | 是 |
| push、发布、账号、协议和其他外部状态 | 按任务与用户授权 | 始终独立裁决 |

## 1. 启动与事实基线

进入工作前先按`GOVERNANCE.md`§10选择恢复模式；无法证明温重绑条件时fail closed并使用`FULL_COLD_RECOVERY`。

`FULL_COLD_RECOVERY`：

1. 从项目Bootstrap开始，按职责读取固定框架版本、PROJECT、STATUS和任务卡。
2. 查询真实`HEAD`、`git status`、相关差异与运行环境；历史状态只作线索。
3. 识别其他会话/用户拥有的文件和暂存内容。
4. 按任务卡读取项目权威文档与相关代码，不以摘要替代原文。

`WARM_TASK_REBIND`：

1. 先证明同一会话的角色、项目ID、Framework版本与已知内容身份、项目权威/current基线仍有效；不能证明即升级完整冷恢复。
2. 增量读取新任务卡、已变化权威与current/热索引，核对actual差异、真实`HEAD`/index、其他owner/保护边界和唯一下一动作；已知exact变化只刷新受影响对象。
3. 明确释放旧任务权限，并从新卡重新取得owner、exact/contingency/forbidden、审核、Git/push/外部动作与保护边界；不因会话复用继承任何旧授权。
4. 记录本次实际增量读取集、未重复读取对象和基线成立理由；这只是任务证据，不新建恢复报告或第二状态文件。

对象、候选或范围被supersede，只作废绑定旧对象的manifest、证据、结论和权限，不自动取消既有执行、审核、owner辅助或其他工作上下文承担后续职责的资格。资格不等于授权：任何复用都必须先对新对象、角色、范围、权限和唯一下一动作完成上述`WARM_TASK_REBIND`；执行者从新卡重新取得写权，审核者还要重新证明未参与受审实质写入且独立性仍成立。

两种模式完成后都必须按任务档位回报足以安全执行的信息。共同最小集是唯一owner、任务/当轮目标、档位与风险、exact/forbidden、验证、Git/外部权限、保护边界和唯一下一动作；只有实际挂载临时角色时才增加执行载体、审核人和消息闭环字段。平台/发行属于`CRITICAL`，还要核对工具与SDK版本、下载/安装/缓存/工程/产物路径、账号/AppID/设备权限以及当前外部状态；未知项标为`UNVERIFIED`，不得用历史摘要补齐。

没有有效任务卡、范围包或文件所有权时，只做只读调查和提出任务卡修订建议。长期角色冷恢复完成只代表可以idle和接单；第一次真实排程前还必须从路线、阶段、热索引和任务卡证明自己知道当前唯一动作。

## 2. 工具驱动注意力与理论建构

“完整阅读”不是机械读完所有文件，而是在风险范围内建构可解释的系统理论。

先用搜索、目录、引用和结构标记建立注意力地图：入口、状态所有者、读写方、调用方、配置、测试、文档、运行时消费者。随后阅读地图覆盖的相关原文，并能回答：

- 这个对象为什么存在？
- 为什么归属于当前模块/层？
- 当前数据和控制如何流动？
- 目标变更应在哪个抽象点发生？
- 新建对象时，现有体系缺了什么，它如何有机融入？

遇到预期外事实时暂停，更新理论、影响范围和方案；不要因已投入时间而坚持错误方向。

在决定修复和证据强度前，先把问题标成`CURRENT_REACHABLE / CONTRACT_REACHABLE / FUTURE_ONLY / UNVERIFIED`：

- 真实生产者、入口、生命周期或trace能到达，才是`CURRENT_REACHABLE`；按实际玩家影响选择集成、浏览器、设备或玩家验证。
- 公共合同允许但当前没有自然producer入口，是`CONTRACT_REACHABLE`；默认用最窄直接反例保护合同，不为它制造假UI、假producer或重型外部证据。
- 当前生产链不可能到达，只属于未来阶段，是`FUTURE_ONLY`；进入未来任务或接口说明，不阻断current候选。
- 无法证明时保持`UNVERIFIED`并只读追producer/consumer，不把“理论上可能”当成已发生风险。

## 3. 权威与冲突裁决

权威层级由项目定义。通用原则：

- 产品/设计原则决定“为什么”和目标体验。
- 规则、接口、数据权威决定机械合同。
- 代码反映当前实际实现，算法实现细节通常以代码和测试为证据。
- 文档与代码不一致时，先判断是实现偏差、文档偏差还是未批准设计变化，不能自动选一边。
- AI 不发明缺失的产品原则。事实可调查；需要新目标、重大取舍或授权时交有权限的角色/用户决定。

命名采用项目统一语言。发现术语冲突时先裁决权威名，再统一传播。

## 4. 工作档位与改前准备

### 4.1 MICRO

- 仅当任务单领域、低风险、可直接验证、无公共合同/持久状态/外部动作/并行owner冲突，且健康owner会话能在同一turn闭合时使用。
- 默认不创建完整任务卡、临时执行者或独立审核者；owner当轮明确目标、exact/forbidden、验证、Git/外部权限，读取直接相关对象并记录结果。
- 有持久卡时使用最小`MICRO`范围摘要；无卡时不运行checker。
- 跨turn、阻断、扩面或准入事实不再成立时，先停写并升级`STANDARD`。不得因`MICRO`跳过工作树保护、真实差异或必要验证。

### 4.2 STANDARD

普通单领域功能、缺陷或跨turn工作使用紧凑任务卡，包含目标/非目标、唯一owner、风险、exact/forbidden、验收、验证、Git/外部权限和唯一下一动作。按实际影响补方案、直接/间接影响、文档/接口/数据同步和1–3项pre-mortem；不机械继承CRITICAL的全字段、角色或完整十二项审查。宿主适配字段只有实际挂载多会话且能减少歧义时才声明。

### 4.3 CRITICAL

跨域公共合同、复杂状态机、核心循环、持久状态、平台/runtime、账号/发布、不可逆动作或缺陷代价高时使用。除`STANDARD`要求外，还必须：

1. 逐项执行十二项方案审查。
2. 建立行为声明清单和关系/依赖影响图。
3. 明确状态所有者、完整生命周期、失败与回滚路径。
4. 先由分管审核方案；跨域或阶段门交主控。
5. 选取必要评审视角，决定是否需要独立盲审。
6. 涉及外部系统时，把下载、安装、协议、登录/绑定、AppID、设备授权、上传、提审和发布拆成独立动作与授权门。

授权来自已批准任务卡和角色权限；不是所有修改都必须再次等待用户或主控逐项批准。Review轮次不是额外阶段门，已冻结范围内的红灯、返工和复审由owner闭合。只有新增公共路径/状态、跨域合同、阶段顺序、owner、产品取舍、质量底线或外部/Git权限时升级。若`MICRO / STANDARD`途中触发`CRITICAL`条件，升级档位不是新建第二流程，而是补齐同一任务缺失的范围、审核和证据门。

## 5. 方案内容标准

方案至少说明：

1. 问题及可复核证据。
2. 目标状态与行为合同。
3. 实现步骤和抽象切入点。
4. 本次、直接、间接影响。
5. 需同步的权威文档、接口、数据、测试与关系图。
6. 最可能失败的三件事及检查动作。
7. 明确不做什么，防止范围漂移。
8. 完成和回滚标准。

对修改对象做“三问”：现有结构是否已解决一部分？是否重叠/冲突？修改后命名、归属、数据流和结构模式是否整体自洽？能扩展现有抽象时不复制第二套路径。

## 6. 安全网与测试

- 重构前先确认 characterization test 或其他可观察安全网；没有安全网时先建立 seam/测试入口。
- 新模块、新状态和新行为必须有直接测试；“旧测试全绿”只说明已有合同未明显破坏。
- 改变有意行为时，先明确新合同，再同步测试，不能把失败测试直接改成绿而不解释行为变化。
- 修改后验证所有调用点和生命周期出口，不只验证被改函数。
- 显式搜索 TODO、null/占位实现、废弃入口和无人消费的状态。

## 7. 实施纪律

- 只修改任务卡拥有的文件，先处理根因和正确抽象。
- 正常条件分支可以存在；禁止用额外 if/else、镜像状态或持久字段掩盖所有权问题。
- 新增持久字段前回答：消费者是谁、为何需跨 tick、能否派生/瞬态、谁写/更新/清除/销毁。
- 触及现有方法时执行 boy-scout 检查：抽象层次和职责问题若直接妨碍本次正确实现，应在本任务内修正；无关问题单独路由。
- 遇到影响范围扩大、权威冲突或风险升级时停止写入，更新任务卡并交审核人决定。
- 条件contingency只能使用建卡时列出的精确路径和触发条件；未列新路径先停写并走范围门，不把Review发现自动升级为主控审批。
- 只从官方来源取得工具、SDK 和引擎安装包；绑定精确版本、字节数、哈希和可用签名。不得把密码、令牌、私钥或个人凭据写入仓库、任务卡或日志。
- 共享工具目录与项目专用 PoC/产物目录分离；候选工程不得未经阶段门进入正式依赖图。

## 8. 发现额外问题时的边界

所有问题都必须记录和分类，但并非全部当批修复：

- 直接导致当前任务错误或阻塞验收：纳入当前任务。
- 当前改动引入：必须当批修复。
- 与当前文件/机制紧密耦合，延期会造成明显重复劳动：建议扩展任务，由审核人批准。
- 无关历史问题：创建候选任务，记录证据、影响和建议领域，不擅自扩张。

旧概念清除的搜索范围跟随概念实际扩散范围，而不是任意限制为当前文件，也不是默认扫描并修复整个仓库。

## 9. 关系图与影响沉淀

项目可维护 `RELATIONSHIPS.md`，记录无法仅靠一次 `rg` 稳定恢复的语义关系：概念扩散到哪些权威文档、改动会影响哪些模块、为何相关。字段的简单引用方通常实时搜索即可，不长期复制。

只记录已批准、跨任务仍稳定的关系。未批准方案留在任务卡；过时关系在同一变更中更新或删除。

## 10. 修改后的验证和审核

任何写入者先按`REVIEW_CHECKLIST.md`自检。`MICRO`由owner承担结果，不制造独立批准；`STANDARD`按风险由领域owner或另一个合格上下文聚焦审核，不机械要求新会话；`CRITICAL`进入`REVIEW`后停止扩大范围，由任务卡指定且未参与实质写入的审核者读取任务卡、权威资料和actual差异。公共合同、持久状态、核心循环、跨域状态机或重大玩家体验变化必须使用与方案设计者不同的合格最终审核者。

有持久卡的任务进入Review时，范围摘要切换为`REVIEW`且expected/actual具体路径集合相等，并由AI把独立机器观察actual传入项目固定版本checker验证声明身份。`CRITICAL`审核输入还要绑定稳定内容对象/section identity、candidate与依赖manifest、验证上限；顶部状态、宿主扩展及执行、审核、Git、交接记录的纯机械落账属于可变区，不自动使内容批准失效。

审核发现问题：标为 `CHANGES_REQUESTED`，执行者修复后从受影响的验证层重新开始；若修复改变方案或影响范围，回到改前准备。

任务卡授权直接审核闭环时，仍按同一§0复审步骤执行，不建立第二流程：执行者只处理已授权范围内返工；候选变化先按内容、依赖、范围、权限/公共合同与纯机械known-exact分类；影响无法证明时完整复审；`RANGE_GATE_REQUIRED`、产品/跨域/owner/质量底线/权限冲突、同一发现复发或轮次上限立即回owner；最终`APPROVED / BLOCKED`、稳定对象、验证上限与残余风险回owner。具体消息发送、条件式确认和宿主字段由对应`HOST_ADAPTER_*.md`定义，不取得写入、范围、Git、阶段或外部权限。

## 11. 文档、状态与交接

- 功能/契约改变时更新实际受影响的权威文档和 DEVLOG；不为“全面同步”争写无关文件。
- 项目资料只放稳定项目身份与例外，项目状态放current，任务卡放执行证据和交接；通用流程只能由固定框架持有，不在项目热入口复制第二套正文。
- 关系图只放已批准的稳定关联。
- 正式文档有机整合目标设计，不引用临时聊天/方案编号作为永久依据。
- 无法当批同步的真实偏差必须绑定负责人和任务，不能只写模糊 TODO。

交接必须包含：结论、用户/产品变化、合同偏差、稳定对象、验证上限、所有权释放、下一动作/裁决请求；完整命令、返工和过程证据留在任务卡。下一会话应能不读聊天记录完成恢复。

## 12. 外部动作与发行收口

1. 任务卡逐项列出已授权和未授权动作。下载授权不包含运行安装包；安装不包含接受协议；登录不包含绑定项目；构建不包含上传；测试版本不包含提审或正式发布。
2. 下载交付记录官方 URL、版本、时间、字节数、SHA-256、签名结果和落盘路径；无法从官方来源确认的候选保持 `BLOCKED` 或 `UNVERIFIED`。
3. 安装交付记录许可接受者、安装/缓存路径、组件版本、环境变量或注册状态、卸载/清理方式；不得擅自接受需要用户主体同意的协议。
4. 构建交付记录输入 commit/配置、工具链版本、产物结构、包体、日志、可复现命令和清理方式。Web 页面产物不能冒充平台发行产物。
5. 账号/AppID/团队角色、设备白名单、测试上传、审核和正式发布分别记录状态与操作者；正式发布必须有用户的当次明确授权。
6. `AI-Workspace`默认分支在`framework/versions/`保留全部稳定版本；同一仓同时承担开发与发行，不再组装第二个发行树。
7. `framework/CURRENT`只在新稳定版本内容批准、完整测试和发行owner收口后更新；现有项目pin不自动改变。tag只是可选审计/下载标记，不能成为注册、恢复或升级前提。
8. 旧项目升级必须直接读取其固定版本目录并严格验证Bootstrap；目录缺失、不完整或模板不匹配一律fail closed，不从tag或当前HEAD猜历史模板。版本进入STABLE即不可原位修改，任何问题一律通过新patch版本修复；是否已被项目消费不改变该规则。

## 13. Git 收口

1. 重新检查 HEAD、status、工作区/暂存区差异和任务所有权；从这些机器事实或冻结manifest取得本任务actual pathset。有持久卡时逐卡传给项目固定版本checker并验证与任务卡声明一致；无卡`MICRO`直接按当轮冻结范围核对。checker不发现Git owner，不能用其通过替代人工范围归属判断。
2. 确认审核结论和任务卡Git权限；条件预授权已满足时不再申请一层机械Git门。
3. 只暂存任务精确路径；检查 cached diff 和 `diff --check`。
4. 运行规定验证，记录真实输出和未验证项。
5. 创建单一逻辑提交并报告哈希；核对commit tree、parent、index、其他owner边界和任务规定的post-commit smoke；已有他人staged内容时不得误带。
6. push/发布需独立授权。内容提交后仍待外部动作的任务保持active；成功后记录外部branch/commit/tag/push等结果再做同ID closure提交并归档，阻断则保持active记录真实状态。

权限错误不等于陈旧锁。先报告真实错误并排查进程/沙箱，不盲删 lock，也不把可由授权流程完成的操作默认甩给用户。

## 14. 沟通标准

- 先给结论、证据、影响和下一步，不输出隐藏思维链。
- 用户质疑时重新查原文和实际状态，不盲从也不固执。
- 首次出现内部编号、缩写和字段时补充含义。
- 不把本应由 AI 调查的事实问题抛给用户；需要用户目标、取舍或新授权时明确请求决定。
- 分管消息是事实、专业建议和裁决申请，不因命令式措辞取得主控权限；主控必须独立区分事实、用户决定、建议和请求。
- 执行者只向唯一owner完整交接一次。完成、真实阻断、范围冲突或需新授权时主动使用当前宿主的消息机制；任务界面状态不能替代回传。
- 独立任务默认异步推进，不靠轮询制造进度感；等待例外、消息确认与直接审核闭环由对应宿主适配定义。
- 宿主适配不得创造第二owner、第二生命周期或新的审核、Git、阶段和外部权限。

## 15. 动态资源与执行载体

资源按最低充分原则选择，项目把实际模型与请求档位映射到下列能力级：

- 机械强校验：边界已冻结、低歧义、结果可直接机器验证。
- 常规执行：中等多文件修改、明确行为合同和直接测试。
- 复杂执行/调查：算法、状态机、生命周期、多域影响或高歧义取证。
- 战略责任：主控、长期分管、重大架构/产品取舍与高风险终审。

任务owner根据复杂度、歧义、风险、验证能力和上下文复用收益记录选择；不能因为便宜而把高风险职责降级，也不能因长期角色资源较高就让所有临时任务机械继承最高档。

载体选择：

- 单turn可完成、无外部等待且owner必须当轮综合：内部子Agent。只有当前turn确实需要结果时才做一次事件汇合。
- 跨turn、预计返工、需要用户/阶段/Git等待、worktree、独立审计记录或直接沟通：独立任务上下文。依赖主动交接，具体消息与等待规则按宿主适配执行。

长期执行/审核上下文只在同owner、同领域、近期明确消费者、上下文健康且确有冷恢复净收益时保留。新任务必须重新授予范围、审核和Git权；旧权限不随上下文继承。没有近期消费者、角色重复、干扰已影响判断或唯一字节已稳定时退出当前热工作集。上下文退出与worktree删除始终分开裁决。

## 16. 会话健康与轮换

- 不做每日/定期健康检查，不为检查唤醒空闲上下文，不以脚本或跨上下文命令自动触发压缩。
- 用户准备判断是否轮换时，可自行决定是否先压缩，然后要求目标会话自检。AI不读取或猜测上下文占用比例。
- 自检输出两项：任务能力`PASS / DEGRADED / FAIL`，上下文干扰`LOW / MEDIUM / HIGH`。必须从Bootstrap、项目权威、有效任务卡和真实仓库重新得到角色、上下游、状态、范围、权限、文件owner、保护边界和唯一下一动作；能复述聊天不算通过。
- `PASS`可继续；`DEGRADED`只完成已冻结窄边界或等待决定；`FAIL`停止新工作、固化交接并建议换会话。用户结合该质量结论与界面可见压缩状态作最终决定。
- supersede本身不是更换工作上下文的理由。只有上下文健康、职责冲突、审核独立性、资源能力档或用户决定要求时才更换。
- 确需更换时，固定顺序是：旧上下文完成可恢复交接；owner把新对象和职责绑定给替换上下文；替换上下文确认能从权威对象恢复并安全继续；随后被替换上下文退出当前热工作集。只有旧上下文仍承担另一项明确职责时才可暂时保留，但必须释放被supersede对象的旧权限，不能以未定义的等待无限占位。

## 17. 任务关闭、试点和证据复用

- active只保留真实下一动作或明确触发器。目标完成且证据稳定后即`CLOSED`并归档，不用范围外push、清理或后继阶段拖延。
- 跨域目标默认保留单父卡；子卡建制必须写明必要性、父卡consumer和退出条件。父卡消费稳定输入后，临时子卡立即`CLOSED`归档；领域方案/验收结论由领域owner持有，主控只处理跨域冲突与阶段门，不重复领域审核。
- 长期父卡在自然边界做`KEEP_THIN`：历史固定到commit/blob，热卡只留current、权威指针、触发器、禁止事项和唯一下一动作。
- 有持久卡的任务在进入`REVIEW`、Git收口和`CLOSED`前，由AI把本任务机器观察actual逐卡传入`framework/versions/<project-pin>/scripts/check-task-card.ps1`；`ACTIVE_WRITE`允许actual具体身份子集，`REVIEW/ACTIVE/CLOSED`要求集合完全相等。`MICRO`无卡不运行checker；legacy无摘要只报告`LEGACY_UNCHECKED`，不触发全仓迁移或第二状态对象。
- 流程/资源试点沿用同一任务生命周期，冻结自然样本、停止线、判定和候选权威落点；停止线到达后必须`KEEP / ADJUST / REJECT`并写回既有权威，不能无限观察或制造样本。1.3.2分级首轮只从10–20个自然关闭任务已有记录提取准备耗时、恢复模式、审核角色数、返工、冲突/缺陷拦截和恢复耗时；缺失值如实保留，不增加逐任务报表或第二套流程。
- 默认交付只有正式权威、当轮结果和存在时的任务卡。无卡`MICRO`不为形式创建报告；独立报告只在多个长期consumer、lineage证据或大型审计确有净收益时创建，并先回答consumer、消费内容、改变的决定和为何现有记录不足。
- `CRITICAL`证据按对象、依赖、fixture、工具链、环境和命令形成有效键；等价未漂移时复用，输入漂移或无法证明等价时重跑受影响门。降本不降低质量门。

## 18. repo-local发现、注册、升级与迁移

### 18.1 冷恢复发现

1. 把用户给出的仓库路径解析为Git顶层；非Git或子目录输入停止。
2. 若`.ai-workspace`存在，严格验证schema2 `repo-local`身份、相对项目根、Bootstrap受管区和固定Framework pin。partial或冲突停止，不回退中央。
3. repo-local不存在时才检查中央legacy `projects/<id>`；其`repositoryPath`必须匹配真实Git顶层。
4. 从当前挂载的AI-Workspace中唯一定位`framework/versions/<pin>`；0个或多个候选都停止。不得用`CURRENT`、tag、HEAD或网络补洞。
5. 按Bootstrap执行`FULL_COLD_RECOVERY`；温重绑仍重新核对任务、HEAD/index、actual范围和授权。

### 18.2 新项目register

`register-project.ps1`只处理两处都不存在的全新项目。默认WhatIf；要求干净Git顶层、无同ID中央legacy和完全不存在的`.ai-workspace`。Apply在项目仓同级隐藏目录生成全部starter文件，strict UTF-8/LF与身份验证完成后同仓rename；不stage/commit。完整同身份重复Apply返回`ALREADY_REGISTERED`；partial、file、reparse或身份冲突不覆盖。

若`framework/CURRENT`仍指向不含repo-local starter的旧版本，默认注册应拒绝，不自动猜最新；owner明确批准后才显式选择1.4.1或更高版本。

### 18.3 同拓扑upgrade

`upgrade-project.ps1`只升级原拓扑。1.3.x中央legacy继续使用发布时模板和可恢复两文件事务；固定旧版本目录缺失时拒绝，不从tag/CURRENT/HEAD降级猜测。1.4+ repo-local升级只替换Bootstrap唯一`FRAMEWORK-MANAGED`区并逐字保留项目自定义后缀；受管区被改写、目标starter拓扑不同或工作树不干净都拒绝。中央→repo-local明确拒绝并回到项目owner另建的一次性专属任务。

### 18.4 中央→repo-local一次性项目边界

Framework 1.4.1不提供中央→repo-local通用命令、跨仓事务状态或恢复引擎。后续项目专属任务可以冻结中央实时文件清单，在项目仓复制并逐文件校验候选，显式转换`project.json`、`BOOTSTRAP.md`和项目根薄入口；该任务不得写回Framework产品能力。

项目仓提交与repo-local完整冷恢复成功前，中央副本始终是唯一权威；失败时删除未提交候选并从冻结输入重新复制。项目仓成功后，中央冻结和删除由后继任务分别授权，不为未来状态制造假UI或双写权威。
