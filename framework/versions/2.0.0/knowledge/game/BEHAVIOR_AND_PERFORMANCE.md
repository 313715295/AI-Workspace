# 行为验证与性能测量

METHOD / REFERENCE_ONLY；内容版本 1；适用于游戏行为修复、算法替换和性能优化。建议先证明结果正确，再比较在相同工作量下的代价。更快但漏做工作不是优化成功。

把目标写成可观察结果：例如相同输入下目标选择正确、不会重复伤害、取消后不再移动。固定场景、输入序列及适用的随机种子，同时保留低帧率、无目标、目标失效等能推翻方案的情形。只有系统本身具有确定性时才要求逐帧完全相同；否则比较明确容差和不变量。

性能实验记录构建、设备、电源/温度条件、实体量、场景、采样范围和单位。区分首次加载与稳态，保留预热设置、测量次数、每次工作量以及原始样本。根据问题报告中位数、尾部或最差帧，样本不足时不把少量观测包装为可靠尾部分布。改变实现前后采用同一口径，记录是否发生分配、等待或工作遗漏。

Unity 的 Profiler 指南建议在目标平台 Player 采样；编辑器共享资源会影响测量，所以编辑器结果适合定位，不能直接证明设备性能。[Unity Collect performance data](https://docs.unity3d.com/6000.0/Documentation/Manual/profiling-collect-data-introduction.html)

Unity Performance Testing 3.2 将预热次数、测量次数与每次迭代数分开，也将每轮 setup/cleanup 排除在方法计时外。因此需说明测量是否包含场景准备及资源释放，而不能只报告一个耗时数字。[Unity Measure.Method](https://docs.unity.cn/Packages/com.unity.test-framework.performance@3.2/manual/measure-method.html)

最小交付可以是一个真实失败场景、对应修复验证、同场景前后样本与限制。微基准只证明该函数/夹具的测量范围；端到端帧时间、目标设备表现、视觉体验和玩家判断各自需要对应证据。结果波动时先检查条件与工作量，不反复跑到出现好看的数字。

代价来自构建、设备和采样时间。小范围正确性修复没有性能疑点时，不为形式强加大规模基准；已有稳定回归覆盖也无需复制实现断言。反例：减少实体数量后比较总耗时、把预热当测量、只看平均 FPS 忽略卡顿，都会掩盖真实问题。对实时任务，项目自行确定预算与统计口径，本方法不规定通用阈值。
