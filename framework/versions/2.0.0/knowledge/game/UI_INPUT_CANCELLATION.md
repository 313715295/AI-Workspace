# UI 与输入取消、失焦

METHOD / REFERENCE_ONLY；内容版本 1；适用拖拽、长按、蓄力、持续移动等跨事件交互。单次无状态点击通常不需要完整状态机。以下实现建议由 Framework 独立整理，平台事件名称只作例子。

常见问题是按下后等不到正常释放：切窗口、关闭面板、设备断开或宿主接管手势后，角色仍移动、拖拽状态残留，甚至把取消当作确认。

先为一次交互保存当前会话标识、输入源、目标及阶段。把成功提交和取消分开；取消统一清除临时状态、停止连续命令和释放捕获，重复取消也安全。异步回调携带原会话标识，目标销毁或会话已更换就忽略。失焦后的恢复由产品决定重新按下或同步当前设备，不能重放已经取消的提交。

Web Pointer Events 规定事件流被抑制时产生 `pointercancel`，释放捕获可产生 `lostpointercapture`；因此只处理 `pointerup` 不够。两种终止通知可能相关联，建议由同一幂等清理入口处理。[W3C Pointer Events](https://www.w3.org/TR/pointerevents/)

Unity Input System 1.4 的设备重置会取消相关 Action，并避免把重置解释为按键释放触发；后台及编辑器焦点配置会影响具体行为。接入时核对项目版本与平台设置。[Unity Input Settings](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.4/manual/Settings.html)

验证可复现序列：按下→移出→取消；按下→失焦→恢复；关闭持有交互的面板；两个指针先后进入；旧异步回调晚到；重复取消。分别观察残留状态、连续命令是否停止、提交次数和恢复后的首个输入。真实触摸/焦点行为要在目标宿主检查，合成事件通过不能代替它。

代价是少量会话状态和统一清理入口。反例：把所有失焦都当全局取消，会破坏明确支持后台操作的应用；把 `pointerleave` 一律当取消，会截断使用指针捕获的合法拖拽。按实际交互合同选择终止条件，不统一禁止后台输入。
