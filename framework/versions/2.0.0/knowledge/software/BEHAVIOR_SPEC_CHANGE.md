# 软件行为规格与变更

类型：METHOD。内容版本：1。维护者：Framework 内容维护者。

本篇提供可选的软件表达方法。项目可以沿用现有需求、接口说明、规格章节和设计模板，不要求另外创建一组文件。规格记录期望行为，设计说明实现取舍，实际证据记录验证结果；三者各有用途。规范维护的责任与时序取[任务实现判断](../../TASK_AND_SCOPE.md)，本篇不另定义审核、接受或采用门，也不因被读取而成为项目规则。

## 何时需要行为规格变化

用户或下游系统依赖的输入、输出、错误语义、条件、例外、兼容承诺发生变化时，先找项目现有的完整行为依据。必要内容可以写在原文档的受影响章节。纯内部重构且这些承诺未变时，保留原规格，在任务中说明实现变化和验证即可。

从实际消费者开始：谁发起操作，依赖什么结果，怎样判断结果错误？例如“保存后再次打开仍能读到原值”是可观察行为；内部函数名、库选择和调用顺序一般由设计说明。只有对消费者构成契约的实现约束才进入规格。

## 当前依据、目标与证据

| 材料 | 记录什么 | 需要核对的范围 |
|---|---|---|
| 当前有效依据 | 当前项目实际采用且生效的行为、条件与例外 | 完整受影响条款、适用版本、维护者、基线及直接依赖 |
| 目标候选 | 本次所求变化及合并后的完整行为 | 哪些是新增、修改、移除或仅重命名；哪些尚待决定 |
| 已接受范围 | 原成果接点接受的精确候选 | 接受对象和必要前置；实际生效、发布或项目采用是否已经发生 |
| 实现证据 | 具体消费者在具体条件下的实际结果 | 命令或操作、退出与观察、失败、未运行及未证明的范围 |

不要用当前源码目录的最新文件替代消费者仍采用的固定版本，也不要把规格中的“应当”写成实现已经通过。设计可引用原任务和规格，避免另抄一份容易失效的要求。方法索引中的 CURRENT 是维护状态，不能证明项目采用或自然应用有效。

## 写清真实增量，保留完整上下文

先定位受影响全文及必要依赖，再写增量。标题和场景同名只能帮助定位，不能证明语义或基线相同。

| 增量 | 最小充分表达 |
|---|---|
| 新增 | 给出完整新行为、触发条件、结果、错误与例外，说明直接消费者 |
| 修改 | 标出原定位和基线，给出合并后完整受影响条款及相关场景，保留未被改变的条件和例外 |
| 移除 | 说明移除理由、依赖旧行为的消费者、替代方案及必要兼容或迁移处置；没有迁移需求时说明依据 |
| 仅重命名 | 写明原名与新名及引用更新，确认行为保持；同时改变行为时按修改处理 |

增量用于说明变化，不能只靠“增加通知”几个字覆盖原文。项目可以用原句式、表格或其他已有载体；这里的分类不要求特定标题层级、解析器或独立 delta 文件。

起草时核对基线，实际落地前再次核对完整对象。并发变化即使没有改同一行，也可能改变条件、失败语义或消费者。保留他人合法变化，形成完整合并候选；候选与后续生效的边界仍按原任务合同处理，不把新的解释藏在“同步”操作中。

## 可观察且能失败的场景

可以用“前置条件；WHEN 触发；THEN 可观察结果”，也可以沿用项目已有格式。THEN 应能区分正确与错误结果，不能只写“调用成功”或某个函数被执行。只覆盖实际风险中的失败、并发、取消、兼容或恢复，不为每句文案编写镜像测试。

下面是匿名教学例，不是产品事实或实测结果：原规则为“普通会话无活动 15 分钟失效；管理会话例外”。他人已合法改为 20 分钟，本次只增加失效通知。完整候选保留 20 分钟和管理会话例外，再加入普通会话失效时的通知；不能从旧增量恢复 15 分钟，也不能丢掉例外。

| 场景 | 可观察结果与证伪点 |
|---|---|
| 普通会话在无活动 15 分钟时访问 | 仍能执行需有效会话的操作；若此时已失效，说明旧基线覆盖了 20 分钟变更 |
| 普通会话在无活动 20 分钟后访问 | 操作被拒绝为会话失效，收到说明需要重新建立会话的通知；仅记录内部回调不证明用户收到结果 |
| 管理会话在相同时间访问 | 保持原例外允许的行为；若也失效或收到普通失效通知，说明完整例外被遗漏 |

上述是供项目选择验证的预期场景，尚未运行。真实测试、人工验证或其他直接证据应引用其原记录，保留环境、输入、结果和局限。场景文字与查询到完整正文都不证明业务实现正确。

## 两段可裁剪模板

按实际问题保留有用项，可以直接作为现有文档章节。项目原模板已经充分时沿用原模板。

```text
行为规格
用途与直接消费者：谁依赖什么可观察行为
当前依据：完整条款定位、适用版本与基线
候选行为：输入、结果、错误、条件、例外与兼容边界
真实增量：新增 / 修改 / 移除 / 仅重命名；合并后完整受影响条款
场景：前置条件；WHEN 具体触发；THEN 可观察且可判错的结果
证据关联：验证计划、实际记录、失败与未证明范围
维护接点：维护者、候选/已接受范围、实际生效或采用的原合同
```

```text
变更设计
问题与目标：引用原任务和行为规格
方案与理由：现有机制、实质可行替代、取舍与直接消费者
状态责任：谁产生、读取、修改和释放；涉及的真实接口与依赖
失败恢复：实际风险中的失败、中断、回退或兼容处置
验证：哪些错误方案应失败，怎样取得直接证据
落地安排：必要规范候选、实施顺序、迁移与真实前置
未解项：影响决定的事实及其承接者，不能藏进实施步骤
```

设计中的未解项若改变目标行为、方案或权限范围，应在对应决定前解决。已经有充分结论的事项引用原材料即可，不为了填模板重复研究或强迫小任务独立设计审核。

## 维护接点与常见反例

项目规格由项目维护者更新，Framework 通用内容由版本维护者更新，共享内容由该来源维护者更新。只读或撤权来源不能由当前读者修改；在本任务说明受影响条款、影响、待决部分及有权承接者，沿已有且获准的接点处理。读取到来源、使用方法、采用规则与本次命中分别核对，知识 FOLLOW 不更新项目 PINNED 规则。

| 容易失真的做法 | 审读时应保留的判断 |
|---|---|
| 只更新进度卡，宣称规范已维护 | 对照本批承诺，查看受影响完整规范候选和维护结果；合法后置项保留真实前置及责任 |
| 精确候选接受后，再以同步名义添加条件 | 新语义回到完整候选及受影响复核，按原接点处理；接受本身不增加写入或生效权限 |
| 接受失败，或目标已被他人合法改变，仍直接覆盖 | 保留失败与他人有效变化；回读基线及影响，不能把归档或文件存在当生效证据 |
| Source 已接受，便写所有项目已更新 | 区分源码接受、发行、宿主安装和每个消费者实际采用 |
| 删除旧行为只写“已废弃” | 查直接消费者、替代及迁移条件，避免留下不可解释的旧数据或调用者 |
| 为纯内部小修复强建规格或读取全部方法 | 按真实契约变化触发，复用原任务与必要验证；方法供给和全文可读不构成自动采用 |

维护方法本身时核对出处、适用范围和反例，同批更新索引中的内容版本、正文身份与核验日期。不将未改变的业务要求另抄成一份知识事实，也不以目录分类替代其维护者和效力。
