# 产物分类：先说明用途，再选择形式

本文是可选 METHOD，contentVersion=1，由 Framework 内容维护者维护。适用于同一文件形式承担不同工作、混合文档难以选择要求、交付集合需要保留组成关系的情形。它提供可裁剪的判断方法，不是全行业编码标准，不要求逐文件登记、搬迁或额外审批。内容是通用原创整理，例子是匿名化教学反例；未据此声称行业合规、真实产品验证或已降低成本。

## 从消费者和问题开始

先说明“谁在什么工作中，用它回答什么问题”。需求、设计、规范、工作方法、实现资产、试验证据和交付集合，是可选的起始业务种类；项目只保留会影响要求、工具或交付的区分。“计划、报告、记录”可以与具体用途组合，不必成为互斥的大分类。

| 描述面 | 需要辨明什么 | 放在哪里 |
|---|---|---|
| 用途与信息种类 | 供谁解决什么问题，是要求、方案、资产还是证据 | 原目录说明、章节、任务交付说明；稳定且影响选择的类型才映射 deliverableType |
| 表现形式 | 文字、代码、数据、位图、矢量、三维、动态影像、声音、工程或组合 | 已有文件/资产信息；影响处理工具、可访问性或交付兼容时说明格式 |
| 行业与专业范围 | 当前涉及哪项专业判断，可同时涉及多个领域 | 项目定义；必要时对应 domain |
| 当前活动与阶段 | 现在调查、设计、制作、验证还是交付 | 当前任务事实，对应 workType / stage；未来目标不能变成当前执行 |
| 版本、状态与证据 | 哪一版在什么范围被采用、检查或接受 | 原版本与证据记录；阶段名、索引 CURRENT 都不代替实际事件 |
| 关系与责任 | 来源、派生、组成、实现/满足、验证、依赖及维护责任 | 已有链接或工程关系；只记录影响使用与变更的关系 |

扩展名说明表示形式，不能独自决定用途。需求规格的 Markdown、PDF 和结构化数据可以是同一信息项的不同表示；项目明确哪个承载当前语义、如何同步和验证一致性，而不是把它们当三个互不相关的要求。同一个 DOCX 含需求、设计与审核意见时，先按章节定位；只有不同责任、消费者或更新周期需要才拆开。成片交付中的视频、音轨、字幕和清单保留组成与版本关系，不能归成“一个 ZIP”后丢掉各自要求。

## 软件与媒体中的易混项

| 相似外观或称呼 | 应保留的区别 | 适用判断的上限 |
|---|---|---|
| 接口说明与 OpenAPI | 接口要求/设计的文字和结构化表示；语义来源由项目明确 | 一致性不等于真实调用行为通过 |
| 代码补丁与测试日志 | 实现和验证记录分别定位，日志绑定被测版本 | 局部测试不能推出设备表现或用户体验 |
| 同为 PNG 的空间关系粗格与摄影分镜 | 前者研究人物/物体关系，后者设计镜头观看方式 | 空间可读或镜头意图不证明实际时间节奏 |
| 角色概念图与运行模型 | 视觉意图、模型/材质及参考/派生关系不同 | 看图不能证明骨骼、碰撞或运行性能 |
| 原始对白与声画试剪 | 表演候选与组合接点试验，绑定真实区间和版本 | 原音自然度与组合节奏/同步需要分别听看 |
| 宣传录屏与缺陷录屏 | 可用同一格式，当前消费目的不同 | 美观展示不自动成为可复现缺陷证据 |
| 候选标准与已采用标准 | 内容建议与当前义务，效力来自项目决定 | 标题写“标准”不使草稿成为 MUST |
| 图纸与物料表、剧本与梗概 | 结构/物料、制作/概述分别供不同消费者使用 | 概念分类不证明制造合规、表演或观众效果 |

当同一对象同时有多个用途，记录这次判断实际涉及的用途，必要时多个类型并存；不要为了压成一个标签丢失要求。表现形式相同不要求复用同一专业标准，形式不同也不必拆散同一信息来源。

## 接到现有四维和项目词表

domain、workType、deliverableType、stage 仍是唯一四维；表示形式、责任、证据状态和关系不另造第五维，也不强塞进这四维。机器如何匹配取当前版本 TOOL_CONTRACT；本文不是第二选择器。配置只保存项目决定采用、当前确有消费需要的词项。

例如项目可以在既有 policy.facetVocabulary 采用以下局部定义；它们是示例，随本文阅读不会自动注册，也不是 native token：

```json
[
  {"dimension":"deliverableType","id":"media:spatial-study","description":"空间关系研究；包括人物位置与遮挡粗格，不包括摄影机观看设计。","aliases":["空间关系粗格"]},
  {"dimension":"deliverableType","id":"media:shot-design","description":"镜头观看设计；包括机位与画面组织，不声称时间节奏已验证。","aliases":["摄影分镜"]}
]
```

供给方维护词义、版本、别名和边界，项目 Owner 按原标准采用/规划责任决定本地映射。名称相同不保证同义：“关键帧”可能是动画姿态、编码帧或图生视频端点；不能把三者直接合成安全别名。存在歧义时核对当前对象与用途，不能取首项。“父类包含子类”可作为知识解释，但规则 selector 必须显式列出适用值，不自动继承。

别名或定义改变时由项目消费差异，不覆盖 native 词项、不悄改旧 selector。未知 token 按合同拒绝；UNKNOWN 是当前分类未知，NOT_APPLICABLE 是确定该维不适用，不能互换。已知边界不符优先排除，辅助关键词不能覆盖它。混合交付只添加本次实际需要的值，不以“以后会制作”触发现在的制作动作。

## 分类不赋予效力

供给目录的 RULE / STANDARD / METHOD / TEMPLATE / KNOWLEDGE_LIBRARY 描述内容种类；需求、设计、资产和项目事实通常不应被塞进 process-policy。方法被引用可以只是参考；规则成为当前义务需要相应项目决定及原治理流程。来源可读、项目已采用、本次规则命中、正文已加载、方法实际有效，是分别核对的事实。

新资料建议与当前规范冲突时，先按当前决定和适用范围处理，不能通过改分类撤销义务。需要进一步诊断、研究和验证时，按需阅读[问题驱动改进](PROBLEM_DRIVEN_IMPROVEMENT.md)；这条链接不要求每次分类都加载另一篇方法。

分类调整保留必要原版本、关系及对消费者的影响。已有表达足够时直接使用，不为了“归一化”破坏旧导航。维护者接收具体误分类反例后修订正文与索引；项目自定是否更新，固定包按发行边界交付。返回[方法入口](../README.md)。
