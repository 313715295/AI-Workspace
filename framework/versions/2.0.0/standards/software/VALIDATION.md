# 软件验证与回归

适用于项目明确采用本标准后的测试设计、维护和结果判断。沿用既有审核与验收安排；测试目的、条件、预期和依据可留在现有代码、任务或变更说明中，无需另建测试卡、全局矩阵或登记表。

## 1. 测什么、依据什么

实现者或测试设计者从现行需求、交付承诺、变更、实际消费者和风险确定范围。承诺的行为与禁止行为、改动可能破坏的关键要求及相关高风险须有验证依据；风险综合失败后果、可能性和影响范围判断。

| 候选对象 | 选择依据与触发 |
|---|---|
| 用户行为与验收场景 | 承诺的正常结果、禁止行为和关键失败场景。 |
| 输入、输出与规则 | 受影响的等价类、边界、条件组合、业务规则和数据不变量。 |
| 接口与依赖 | 实际生产者与直接消费者、公开或实际内部合同、依赖失败处理。 |
| 状态与副作用 | 受影响的状态、持久化和外部效果；涉及重试、幂等、取消、中断或恢复时验证相应行为。 |
| 专项质量风险 | 交付要求或实际风险触发的权限、安全、并发、兼容迁移、性能容量、可访问性、平台或设备验证。 |
| 缺陷与回归 | 已确认缺陷的有效复现、修复目标及受影响的相邻行为。 |

按影响和触发选用，不要求逐项执行。无实际消费者、已退出支持或未受影响的对象不自动加入；不能因验证困难省略承诺或相关高风险。依据可来自自动化、直接检查、人工验证或有效旧结果（§5）；是否新增用例按§4判断。

## 2. 有效测试

测试在给定前提和触发下，将可观察结果与预期比较以检出错误；断言是作出该判定的检查。预期来自有效行为要求、业务规则或合同，不能由当前实现自定；预期不明时补充依据或标为探索性观察。

有效测试能到达目标机制，观察与预期能区分相应错误。按目标构造的非法输入或故障也可以是有效前提。按需检查返回值、状态、副作用、错误或质量约束；接口成功不独自证明业务完成。无关前提提前拒绝、替身替掉目标、复制实现分支、只找文案或只看总PASS，均不能证明目标行为。

负例可能被前置失败掩盖时，先证合法基线，再改变被测因素，核对对应错误和应保持的状态，按需恢复复验；简单用例不必普遍增加整套前后运行。检错能力仍有疑问时，可做少量定向故障注入或变异试验。

## 3. 选择最低充分层级

| 层级 | 主要验证目的 |
|---|---|
| 小范围逻辑 | 规则计算、等价类和边界，快速定位错误。 |
| 组件或合同 | 实际接口的接收、返回、拒绝及消费者约定。 |
| 集成 | 组件连接、序列化、存储或外部依赖的真实交互。 |
| 端到端 | 代表性用户流程在所需环境中的最终结果。 |
| 静态结构 | 有独立要求的语法、文档格式、包结构、引用、边界或完整性。 |

条件组合尽量放在能充分检错的小层级，高层保留接线、持久化、并发、平台等独有风险。替身只隔离非目标依赖；浏览器、设备、性能或恢复属于交付要求时，保留相应直接验证。结构检查、运行行为和文档语义各有目的，不能互相替代；文档语义由内容审核判断。

## 4. 维护现有用例

变化时先查已有覆盖，再决定用例如何维护；用例复用与旧执行结果复用分别判断。

| 决定 | 适用条件与覆盖承接 |
|---|---|
| 复用 | 预期仍有效，已有用例能检出本次风险。 |
| 修改 | 要求或输入合同已变，更新预期、数据或接点，保留有效边界。 |
| 参数化 | 场景共用验证逻辑、差异可用数据表达，失败仍能定位。 |
| 合并 | 检验相同风险且无独有约束，保留者承担全部有效检错目的。 |
| 下沉 | 小层级足以验证条件，高层保留独有交互与关键流程。 |
| 增加 | 存在已有用例不能检出的有效风险，在最低充分层级补齐。 |
| 退役或删除 | 要求退出或有效覆盖由保留者承担，说明依据与承接。 |

同名、同输入、同返回或共同入口不证明重复，不同层可能检出不同错误。用例维护、本次回归选择和执行排序分别判断；未运行或临时跳过不等于永久退役。

## 5. 回归选择与结果复用

按真实变化、直接消费者和相关依赖选回归。失败先做最小判别，再补必要相邻场景和完整流程；扩大范围须有变化、失败、未解风险或既定完整性要求。

复用结果须确认目标与定义、相关输入和依赖、命令与运行条件仍适用，原结果完整可信，环境与清理满足隔离要求。保留原执行事实，说明本次复用依据；事实不足或依赖未知时，对受影响范围补证或重跑。失败、部分覆盖、中断、跳过或执行漂移不能改称完整通过，不以持久PASS标签代替判断。

## 6. 夹具、失败与成本

使用满足目标的合法最小夹具，隔离真实数据、外部副作用和共享状态；目标需要时才构造完整环境。复位须针对正确对象，确认无活动进程或服务继续改写，并核对恢复状态。模拟、隔离环境与真实宿主、设备或服务结果分别标识。

预期或断言错误是测试问题；前提不满足是夹具或环境问题；故障本身是测试目标时，按产品要求判断。有效前提下违反要求才构成相应产品缺陷。证据不足保留未知，不放宽正确校验或修改预期换取通过。

保留实际命令或操作、终态和必要原始输出，区分失败、中断、未运行、跳过与未知，修复后通过不抹去原失败。长测试及时保存输出和阶段信息并取得真实终态；无输出不单独决定成功、故障或取消，停止与续作按现有执行约束。

成本改善从既有入口实测，区分准备、执行和核验，说明样本、输入与环境。包含或并行阶段耗时不直接相加，断言数、静态调用数和重跑次数不用于推算提速。依赖耦合造成重复重型准备时，先改善可测试性，不只删断言换速度。

## 7. 交付依赖模型行为时

仅在交付效果依赖模型或agent行为时进行相应评估；软件由AI编写不自动适用。确定性工具测试不能独自证明模型理解请求、选择动作或完成任务。

按目标选自然任务或受控代表场景及关键反例，检查实际成果、必要状态、约束和轨迹，保留措辞不同但等价合法的结果。模型自述、模拟返回、回执或脚本结果只证明各自范围，不替代实际任务效果，也不要求证明模型脑中持有全文。优先复用已有任务证据，缺少场景注明待验，不默认新增模型调用或评测平台。

## 8. 审核与验收判断

先审检错能力及合并、退役的覆盖承接，再看真实结果和限制。承诺与相关高风险有可判别依据，直接消费者及受影响失败、状态路径得到相称覆盖，才支持相应范围的通过；未验或未知项说明影响与限制，不计入完整通过。数量、通过率或覆盖率不能独自证明质量；不设统一层级比例、覆盖率或变异率，不要求全量变异或逐用例独审。

例如，订单上限从100改为200：更新原边界，验证200接受、201拒绝并保持应有状态；身份校验先失败不能证明数量限制。接口传参和落库若分别检查传输与持久化错误，仍各有保留价值。
