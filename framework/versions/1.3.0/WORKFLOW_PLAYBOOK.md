# 工作流程手册 v1.3.0

本手册回答“怎么工作”；`REVIEW_CHECKLIST.md` 回答“怎么审核”。项目和任务卡可以提高要求，不能静默降低框架要求。

## 0. 唯一端到端流程

长期责任只有主控与领域分管两层；执行者和独立审核者按任务临时挂载。每张任务只有一个长期owner，该owner同时是唯一调度者。完整路径只有这一条：

1. **接收与路由**：主控判断主领域、跨域关系和阶段顺序。纯领域问题交分管直接调查和讨论；跨域目标默认指定一个主owner和一张父卡，不建立双owner，也不按领域数量机械拆包。只有独立生命周期/owner字节/外部状态/可关闭交付物/必须保留的审核结论才建子卡，并绑定父卡consumer与退出条件。
2. **一次授权**：主控只冻结目标、阶段/公共边界、owner、禁止事项、外部/Git权限和升级条件，不替分管写日常方案与pathset。领域owner在边界内不逐项向主控申请。
3. **任务建制**：owner核对producer、direct consumer、tests、runner/manifest、docs和contingency closure；冻结exact/contingency/forbidden范围、行为不变量、执行载体/资源、审核人、证据门、Git预授权和回传对象。新建/实质修改卡只在唯一机械摘要声明current exact与具体expected/actual pathset，历史exact记录不作current输入；AI从git status/diff或manifest取得本任务机器观察actual并逐卡传给检查器，进入Review前必须通过，范围不完整时只调查不写入。
4. **执行与复审**：执行者在冻结范围内实施、自检并向owner交接一次；owner先冻结candidate manifest、稳定内容对象/section identity、依赖manifest和验证上限，再闭合红灯、返工和Review轮次。任务卡预授权直接审核闭环时，执行者与指定独立审核者可在冻结范围和停止线内直接传递候选、发现与窄返工，owner只接收Review开始通知、升级冲突和最终结论。实质写入者不得自批；重型公共合同、持久状态、核心循环、跨域状态机或重大玩家体验变化的最终审核人必须与方案设计者不同。
5. **提交与回报**：任务卡已预授权本地Git时，审核通过后由指定closer把机器观察actual逐卡传入检查器，再逐项stage、检查cached对象、正常hook提交，并复核commit tree、parent、index、非任务边界和最窄post-commit smoke。push、发布与外部状态始终另门；内容提交后仍有外部发布的同一卡保持active，外部成功并落账后才用closure提交归档。领域owner只向主控发送一次阶段所需摘要。
6. **阶段收口**：主控只核对稳定对象、跨域/阶段影响、所有权释放和下一阶段，不重复领域完整审核或重跑同一有效键。
7. **关闭与恢复**：owner只关闭并归档所有授权动作和外部结果都已真实完成的任务；外部发布阻断时原卡保持active并记录真实状态。被父卡消费的临时领域包立即退出热入口。正式权威存稳定合同，任务卡存过程与证据，项目状态存current。会话释放旧权限后按复用条件idle或归档；首次进入或基线不可证明时做`FULL_COLD_RECOVERY`，同一健康会话且基线可证明时按`WARM_TASK_REBIND`增量重绑，不依赖聊天摘要或继承旧权限。

默认决定边界：

| 事项 | 默认决定者 | 是否升级主控 |
|---|---|---|
| 本域私有实现、算法/样本校正、exact或已列contingency内返工 | 领域分管 | 否 |
| 已冻结任务的执行资源、测试组合、Review轮次、预授权本地Git | 任务owner | 否 |
| 单领域玩家可见复杂行为 | 分管直接与用户确认并持久化 | 仅改变阶段/公共合同/owner时 |
| 新公共接口/持久状态、跨域合同、所有权冲突或明显风险升级 | 主控 | 是 |
| 路线、阶段优先级、质量底线、重大产品取舍 | 主控整理；需用户权限的部分由用户决定 | 是 |
| push、发布、账号、协议和其他外部状态 | 按任务与用户授权 | 始终独立裁决 |

## 1. 启动与事实基线

进入工作前先按`GOVERNANCE.md`§10选择恢复模式；无法证明温重绑条件时fail closed并使用`FULL_COLD_RECOVERY`。

`FULL_COLD_RECOVERY`：

1. 从项目Bootstrap开始，按职责读取固定框架版本、PROJECT、STATUS和任务卡。
2. 查询真实`HEAD`、`git status`、相关差异与运行环境；历史状态只作线索。
3. 识别其他会话/用户拥有的文件和暂存内容。
4. 按任务卡读取项目权威文档与相关代码，不以摘要替代原文。

`WARM_TASK_REBIND`：

1. 先证明同一会话的角色、项目ID、Framework版本与已知内容身份、项目权威/current基线仍有效；不能证明即升级完整冷恢复。
2. 增量读取新任务卡、已变化权威与current/热索引，核对actual差异、真实`HEAD`/index、其他owner/保护边界和唯一下一动作；已知exact变化只刷新受影响对象。
3. 明确释放旧任务权限，并从新卡重新取得owner、exact/contingency/forbidden、审核、Git/push/外部动作与保护边界；不因会话复用继承任何旧授权。
4. 记录本次实际增量读取集、未重复读取对象和基线成立理由；这只是任务证据，不新建恢复报告或第二状态文件。

两种模式完成后都必须回报长期owner/唯一调度者、任务、执行载体/资源、审核人、风险、目标/非目标、写入范围、Git/外部权限、保护边界和唯一下一动作。平台/发行任务还要核对工具与SDK版本、下载/安装/缓存/工程/产物路径、账号/AppID/设备权限以及当前外部状态；未知项标为`UNVERIFIED`，不得用历史摘要补齐。

没有有效任务卡、范围包或文件所有权时，只做只读调查和提出任务卡修订建议。长期角色冷恢复完成只代表可以idle和接单；第一次真实排程前还必须从路线、阶段、热索引和任务卡证明自己知道当前唯一动作。

## 2. 工具驱动注意力与理论建构

“完整阅读”不是机械读完所有文件，而是在风险范围内建构可解释的系统理论。

先用搜索、目录、引用和结构标记建立注意力地图：入口、状态所有者、读写方、调用方、配置、测试、文档、运行时消费者。随后阅读地图覆盖的相关原文，并能回答：

- 这个对象为什么存在？
- 为什么归属于当前模块/层？
- 当前数据和控制如何流动？
- 目标变更应在哪个抽象点发生？
- 新建对象时，现有体系缺了什么，它如何有机融入？

遇到预期外事实时暂停，更新理论、影响范围和方案；不要因已投入时间而坚持错误方向。

## 3. 权威与冲突裁决

权威层级由项目定义。通用原则：

- 产品/设计原则决定“为什么”和目标体验。
- 规则、接口、数据权威决定机械合同。
- 代码反映当前实际实现，算法实现细节通常以代码和测试为证据。
- 文档与代码不一致时，先判断是实现偏差、文档偏差还是未批准设计变化，不能自动选一边。
- AI 不发明缺失的产品原则。事实可调查；需要新目标、重大取舍或授权时交有权限的角色/用户决定。

命名采用项目统一语言。发现术语冲突时先裁决权威名，再统一传播。

## 4. 风险分层后的改前准备

### 4.1 轻型

- 确认任务卡、直接影响和回退方式。
- 读取直接相关对象，记录简短计划和验证。
- 不得因“轻型”跳过工作树保护和实际差异检查。

### 4.2 中型

必须输出：问题、目标、非目标、方案步骤、直接/间接影响、文档/接口/数据同步、风险、验证和完成标准，并做三项pre-mortem。写前还要显式核对producer、direct consumer、tests、runner/manifest、docs和contingency closure，冻结exact/contingency/forbidden范围。

### 4.3 重型

除中型要求外，还必须：

1. 逐项执行十二项方案审查。
2. 建立行为声明清单和关系/依赖影响图。
3. 明确状态所有者、完整生命周期、失败与回滚路径。
4. 先由分管审核方案；跨域或阶段门交主控。
5. 选取必要评审视角，决定是否需要独立盲审。
6. 涉及外部系统时，把下载、安装、协议、登录/绑定、AppID、设备授权、上传、提审和发布拆成独立动作与授权门。

授权来自已批准任务卡和角色权限；不是所有修改都必须再次等待用户或主控逐项批准。Review轮次不是额外阶段门，已冻结范围内的红灯、返工和复审由owner闭合。只有新增公共路径/状态、跨域合同、阶段顺序、owner、产品取舍、质量底线或外部/Git权限时升级。

## 5. 方案内容标准

方案至少说明：

1. 问题及可复核证据。
2. 目标状态与行为合同。
3. 实现步骤和抽象切入点。
4. 本次、直接、间接影响。
5. 需同步的权威文档、接口、数据、测试与关系图。
6. 最可能失败的三件事及检查动作。
7. 明确不做什么，防止范围漂移。
8. 完成和回滚标准。

对修改对象做“三问”：现有结构是否已解决一部分？是否重叠/冲突？修改后命名、归属、数据流和结构模式是否整体自洽？能扩展现有抽象时不复制第二套路径。

## 6. 安全网与测试

- 重构前先确认 characterization test 或其他可观察安全网；没有安全网时先建立 seam/测试入口。
- 新模块、新状态和新行为必须有直接测试；“旧测试全绿”只说明已有合同未明显破坏。
- 改变有意行为时，先明确新合同，再同步测试，不能把失败测试直接改成绿而不解释行为变化。
- 修改后验证所有调用点和生命周期出口，不只验证被改函数。
- 显式搜索 TODO、null/占位实现、废弃入口和无人消费的状态。

## 7. 实施纪律

- 只修改任务卡拥有的文件，先处理根因和正确抽象。
- 正常条件分支可以存在；禁止用额外 if/else、镜像状态或持久字段掩盖所有权问题。
- 新增持久字段前回答：消费者是谁、为何需跨 tick、能否派生/瞬态、谁写/更新/清除/销毁。
- 触及现有方法时执行 boy-scout 检查：抽象层次和职责问题若直接妨碍本次正确实现，应在本任务内修正；无关问题单独路由。
- 遇到影响范围扩大、权威冲突或风险升级时停止写入，更新任务卡并交审核人决定。
- 条件contingency只能使用建卡时列出的精确路径和触发条件；未列新路径先停写并走范围门，不把Review发现自动升级为主控审批。
- 只从官方来源取得工具、SDK 和引擎安装包；绑定精确版本、字节数、哈希和可用签名。不得把密码、令牌、私钥或个人凭据写入仓库、任务卡或日志。
- 共享工具目录与项目专用 PoC/产物目录分离；候选工程不得未经阶段门进入正式依赖图。

## 8. 发现额外问题时的边界

所有问题都必须记录和分类，但并非全部当批修复：

- 直接导致当前任务错误或阻塞验收：纳入当前任务。
- 当前改动引入：必须当批修复。
- 与当前文件/机制紧密耦合，延期会造成明显重复劳动：建议扩展任务，由审核人批准。
- 无关历史问题：创建候选任务，记录证据、影响和建议领域，不擅自扩张。

旧概念清除的搜索范围跟随概念实际扩散范围，而不是任意限制为当前文件，也不是默认扫描并修复整个仓库。

## 9. 关系图与影响沉淀

项目可维护 `RELATIONSHIPS.md`，记录无法仅靠一次 `rg` 稳定恢复的语义关系：概念扩散到哪些权威文档、改动会影响哪些模块、为何相关。字段的简单引用方通常实时搜索即可，不长期复制。

只记录已批准、跨任务仍稳定的关系。未批准方案留在任务卡；过时关系在同一变更中更新或删除。

## 10. 修改后的验证和审核

执行者先按`REVIEW_CHECKLIST.md`自检并提供证据，但不能自批。进入`REVIEW`后停止扩大范围，由任务卡指定且未参与实质写入的审核者读取任务卡、权威资料和actual差异。轻中型不机械要求新会话；重型公共合同、持久状态、核心循环、跨域状态机或重大玩家体验变化必须使用与方案设计者不同的合格最终审核者。

进入Review时，审核输入绑定稳定内容对象/section identity、candidate与依赖manifest、验证上限；任务卡机械摘要切换为`REVIEW`且expected/actual具体路径集合相等，并由AI把独立机器观察actual传入检查器验证声明身份。顶部状态/actor及执行、审核、Git、交接记录的纯机械落账属于可变区，不自动使内容批准失效。

审核发现问题：标为 `CHANGES_REQUESTED`，执行者修复后从受影响的验证层重新开始；若修复改变方案或影响范围，回到改前准备。

任务卡授权直接审核闭环时，按同一§0复审步骤执行，不建立第二流程：

1. 执行者稳定候选并冻结actual manifest/证据，作为唯一发送方向owner发送一次Review开始通知，再直接发送给指定审核者；固定对象发送成功后立即停写，不等待ACK。审核者默认以第一条实质回复同时作为ACK；只有不能立即开始、需要显式保留异步交接，或候选identity/manifest、范围、独立性、权限异常或存疑时，才向执行者单独发送一次条件式ACK或阻断说明，不向owner重复发送阶段通知，也不取得写入、范围、Git、阶段或外部权限。
2. 审核者独立取证；范围内`CHANGES_REQUESTED`可直接发送给执行者，执行者只做exact/已列contingency内且不改变产品、公共合同、质量门或权限的窄返工。
3. 每轮返工先分类known-exact delta：内容/依赖/范围/权限/公共合同变化更新受影响对象与有效键并重审受影响层；纯机械状态、审核记录或可证明known-exact变化只增量重绑。未受影响批准不机械整包重跑；无法证明影响面时fail closed并做完整相关审核。
4. `RANGE_GATE_REQUIRED`、产品/跨域/owner/质量/权限冲突、同一发现按卡复发或达到卡内直返轮次上限时，立即停止并回owner。owner接管并由自己冻结、委派或续审时，机械notifier使用`NONE`，不制造owner通知自己的阶段消息；普通执行者/审核者Review不得使用`NONE`。
5. 最终`APPROVED / BLOCKED`、稳定对象、验证上限与残余风险由审核者直接回owner。审核者不授权Git、阶段或外部动作，owner仍负责这些裁决。

## 11. 文档、状态与交接

- 功能/契约改变时更新实际受影响的权威文档和 DEVLOG；不为“全面同步”争写无关文件。
- 项目资料只放稳定项目身份与例外，项目状态放current，任务卡放执行证据和交接；通用流程只能由固定框架持有，不在项目热入口复制第二套正文。
- 关系图只放已批准的稳定关联。
- 正式文档有机整合目标设计，不引用临时聊天/方案编号作为永久依据。
- 无法当批同步的真实偏差必须绑定负责人和任务，不能只写模糊 TODO。

交接必须包含：结论、用户/产品变化、合同偏差、稳定对象、验证上限、所有权释放、下一动作/裁决请求；完整命令、返工和过程证据留在任务卡。下一会话应能不读聊天记录完成恢复。

## 12. 外部动作与发行收口

1. 任务卡逐项列出已授权和未授权动作。下载授权不包含运行安装包；安装不包含接受协议；登录不包含绑定项目；构建不包含上传；测试版本不包含提审或正式发布。
2. 下载交付记录官方 URL、版本、时间、字节数、SHA-256、签名结果和落盘路径；无法从官方来源确认的候选保持 `BLOCKED` 或 `UNVERIFIED`。
3. 安装交付记录许可接受者、安装/缓存路径、组件版本、环境变量或注册状态、卸载/清理方式；不得擅自接受需要用户主体同意的协议。
4. 构建交付记录输入 commit/配置、工具链版本、产物结构、包体、日志、可复现命令和清理方式。Web 页面产物不能冒充平台发行产物。
5. 账号/AppID/团队角色、设备白名单、测试上传、审核和正式发布分别记录状态与操作者；正式发布必须有用户的当次明确授权。

## 13. Git 收口

1. 重新检查 HEAD、status、工作区/暂存区差异和任务所有权；从这些机器事实或冻结manifest取得本任务actual pathset，逐卡传给检查器并验证与任务卡声明完全一致，不用全仓扫描结果替当前任务自报归属。
2. 确认审核结论和任务卡Git权限；条件预授权已满足时不再申请一层机械Git门。
3. 只暂存任务精确路径；检查 cached diff 和 `diff --check`。
4. 运行规定验证，记录真实输出和未验证项。
5. 创建单一逻辑提交并报告哈希；核对commit tree、parent、index、其他owner边界和任务规定的post-commit smoke；已有他人staged内容时不得误带。
6. push/发布需独立授权。内容提交后仍待外部动作的任务保持active；成功后记录外部branch/commit/tag/push等结果再做同ID closure提交并归档，阻断则保持active记录真实状态。

权限错误不等于陈旧锁。先报告真实错误并排查进程/沙箱，不盲删 lock，也不把可由授权流程完成的操作默认甩给用户。

## 14. 沟通标准

- 先给结论、证据、影响和下一步，不输出隐藏思维链。
- 用户质疑时重新查原文和实际状态，不盲从也不固执。
- 首次出现内部编号、缩写和字段时补充含义。
- 不把本应由 AI 调查的事实问题抛给用户；需要用户目标、取舍或新授权时明确请求决定。
- 分管消息是事实、专业建议和裁决申请，不因命令式措辞取得主控权限；主控必须独立区分事实、用户决定、建议和请求。
- 执行者只向唯一owner完整交接一次。完成、真实阻断、范围冲突或需新授权时主动使用当前环境的消息机制唤醒owner；任务final、侧栏完成或idle不能替代回传。任务卡授权直接审核闭环时，Review开始通知、升级停止线和审核者最终回传是该同一交接路径的阶段消息，不产生第二owner或要求owner逐轮转述。
- owner不做短周期轮询。只有用户要求、超时或疑似失联时读取一次状态快照；不以持续线程等待或轮询维持独立任务续跑。

## 15. 动态资源与执行载体

资源按最低充分原则选择，项目把实际模型与请求档位映射到下列能力级：

- 机械强校验：边界已冻结、低歧义、结果可直接机器验证。
- 常规执行：中等多文件修改、明确行为合同和直接测试。
- 复杂执行/调查：算法、状态机、生命周期、多域影响或高歧义取证。
- 战略责任：主控、长期分管、重大架构/产品取舍与高风险终审。

任务owner根据复杂度、歧义、风险、验证能力和上下文复用收益记录选择；不能因为便宜而把高风险职责降级，也不能因长期角色资源较高就让所有临时任务机械继承最高档。

载体选择：

- 单turn可完成、无外部等待且owner必须当轮综合：内部子Agent。只有当前turn确实需要结果时才做一次事件汇合。
- 跨turn、预计返工、需要用户/阶段/Git等待、worktree、独立审计记录或直接沟通：独立任务会话。依赖主动消息交接，不要求owner保持等待。

长期执行/审核会话只在同owner、同领域、近期明确消费者、上下文健康且确有冷恢复净收益时保留。新任务必须重新授予范围、审核和Git权；旧权限不随会话继承。没有近期消费者、角色重复、干扰已影响判断或唯一字节已稳定时归档。会话归档与worktree删除始终分开裁决。

## 16. 会话健康与轮换

- 不做每日/定期健康检查，不为检查唤醒idle会话，不以脚本或跨会话命令自动触发compact。
- 用户准备判断是否轮换时，可自行决定是否先压缩，然后要求目标会话自检。AI不读取或猜测上下文占用比例。
- 自检输出两项：任务能力`PASS / DEGRADED / FAIL`，上下文干扰`LOW / MEDIUM / HIGH`。必须从Bootstrap、项目权威、有效任务卡和真实仓库重新得到角色、上下游、状态、范围、权限、文件owner、保护边界和唯一下一动作；能复述聊天不算通过。
- `PASS`可继续；`DEGRADED`只完成已冻结窄边界或等待决定；`FAIL`停止新工作、固化交接并建议换会话。用户结合该质量结论与界面可见压缩状态作最终决定。

## 17. 任务关闭、试点和证据复用

- active只保留真实下一动作或明确触发器。目标完成且证据稳定后即`CLOSED`并归档，不用范围外push、清理或后继阶段拖延。
- 跨域目标默认保留单父卡；子卡建制必须写明必要性、父卡consumer和退出条件。父卡消费稳定输入后，临时子卡立即`CLOSED`归档；领域方案/验收结论由领域owner持有，主控只处理跨域冲突与阶段门，不重复领域审核。
- 长期父卡在自然边界做`KEEP_THIN`：历史固定到commit/blob，热卡只留current、权威指针、触发器、禁止事项和唯一下一动作。
- 新建/实质修改任务卡在进入`REVIEW`、Git收口和`CLOSED`前，由AI把本任务机器观察actual逐卡传入`scripts/check-task-card.ps1`；`ACTIVE_WRITE`允许actual具体身份子集，`REVIEW/ACTIVE/CLOSED`要求集合完全相等。legacy无摘要只报告`LEGACY_UNCHECKED`，不触发全仓迁移或第二状态对象。
- 流程/资源试点沿用同一任务生命周期，冻结自然样本、停止线、判定和候选权威落点；停止线到达后必须`KEEP / ADJUST / REJECT`并写回既有权威，不能无限观察或制造样本。
- 默认交付只有正式权威与任务卡。独立报告只在多个长期consumer、lineage证据或大型审计确有净收益时创建，并先回答consumer、消费内容、改变的决定和为何任务卡不足。
- 重型证据按对象、依赖、fixture、工具链、环境和命令形成有效键；等价未漂移时复用，输入漂移或无法证明等价时重跑受影响门。降本不降低质量门。
