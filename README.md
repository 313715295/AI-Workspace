# AI Workspace Framework

AI Workspace Framework 用于用户与 AI 的长期项目治理与协作，目标是在保障交付质量的前提下，降低沟通、执行、验证和返工总成本。它保存目标与验收要求、项目事实、规则和任务进展，明确责任与协作方式，让跨会话工作能够继续。

适合需要跨会话继续工作、多人或多个 AI 会话协作、复用团队标准的项目。它不替代业务代码框架或现有开发工具。

## 它能帮助你做什么

- **接续工作**：把当前目标、任务、决定和结果保存在项目中，后续会话按需恢复，减少重复交代背景。
- **组织协作**：明确项目和领域负责人，按实际需要安排执行者与独立审查，让结果直接回到负责的人。
- **保障交付质量**：围绕目标制定验收要求，组织自测、必要的独立审查和最终验收，明确已完成与待解决事项。
- **控制操作范围**：按项目授权和保护要求检查修改、测试、Git、推送及外部操作。
- **受控自动化与恢复**：在明确授权内衔接可预测步骤，以真实结果推进；中断后核对原动作与现存状态，再继续或恢复。
- **减少重复工作**：按需加载规则，健康续作复用有效上下文，减少重复恢复、材料读取和不必要的交接。
- **动态选择资源**：根据任务难点和质量要求，选择足够的模型与推理强度；结合执行、统筹和返工成本，在需要时调整。
- **复用项目标准**：引用已有资料及项目内外的公共标准，保留项目自己的组织方式，无须先重写文档。
- **问题驱动的改进**：由负责该问题的任务判断根因、修正和后续责任，按缺口选择学习内容与来源，落实到具体改变和对应验证，保留条件、失败与下次入口。2.0 源码候选提供[产物分类与学习方法](framework/versions/2.0.0/knowledge/README.md)；可用内容、自然应用效果与版本发行分别验证。

## 开始使用

当前实现与验证主要面向 **Windows、PowerShell 7 和 Codex**。开发中的 2.0 升级将普通项目的注册、升级和恢复绑定到明确项目目录；普通加载、分析、写测和审核无需 Git。实际 Git 动作及 Framework Maintenance 的双仓拓扑仍验证 Git 条件。已发行包能力以其随包说明为准；2.0 当前仍为不具备普通正式采用资格的候选，本地候选试点须走明确的试点准入。接入时按所选固定版本声明定位项目入口；当前2.0目标由项目AGENTS导航固定Bootstrap，旧navigation1/2沿各自原Skill。

1. 从 [发行页面](https://github.com/313715295/AI-Workspace/releases)选择版本，下载用户 ZIP 并解压到自己选择的目录。
2. 先创建或打开目标项目，从项目根目录启动 AI 会话；说明采用意图并提供运行包目录。
3. 由 AI 按[接入指引](framework/PROJECT_ADOPTION.md)检查环境、说明实际改动并完成接入，报告结果和未完成事项。

例如：

```text
请将当前项目接入 AI Workspace Framework。
运行包位于：C:\tools\AI-Workspace
请按包内指引检查该版本是否适合采用，保留已有项目文档，并说明接入结果。
```

当前项目由会话所在的项目根目录确定，接入提示无需重复填写项目路径或名称。AI 优先沿用已确认的项目名称，未明确命名时使用目录名，并整理注册工具所需的内部项目 ID；用户希望使用其他名称时可主动补充。只有目标目录不明确或命名存在冲突时才需要询问。

升级前保留原运行包与在途动作材料。新候选对旧来源的识别、回滚和原动作收口分别验证，完成后再切换到新入口；源码修复与测试通过后仍须取得新固定分发资格，并由各项目明确采用。

带 `snapshot` 的发行包用于明确选择的候选试点，`release` 用于稳定发行。支持首次候选注册且资格完整的固定 2.0 snapshot 可由新项目显式接入；AI 按包内指引预览，并准备“完成本项目接入并开始治理”的有限任务。开发目录和旧 snapshot 不因名称获得这项能力。用户自行选择解压位置，可以独立存放，也可以由多个项目共用。各项目分别决定何时升级，发布新包不会自动改变现有项目。

## 日常如何协作

向项目 AI 说明目标即可，例如“继续完成这项功能，并验证验收场景”。需要项目治理事实时，从项目AGENTS定位所采用固定版本的Bootstrap；旧版本继续使用其声明的Skill入口。AGENTS导航与用户约定分区保存，迁移和刷新保留原约定及后续收窄、撤回，不重新追加默认授权。连续工作复用仍有效的上下文；源码候选在真实加载时按意图选择、同次去重、组装完整正文，同活动普通范围或本地配套操作变化经当前准入核对后不重载。真实活动切换、要求变化或恢复时完整加载，旧固定版本仍走各自合同。候选模型显示只给完整必要正文、有序短引用、义务与实际限制，机器校验资料由程序保留。

项目主控承担持续项目责任，成果负责人负责当前有限成果的规划、实施、验证与收尾，完成后释放活跃责任。双方都可按具体专业缺口安排专家并直接消费结果。同一未完成成果或同审有界修复复审可续健康且合格的原会话；新有限成果、新独审默认新会话。已关闭或归档的有限会话不默认恢复改名接新活，长期保留须有真实持续职责；原事必要补正可回原会话。成果已交付、原结果已消费且无后续职责时，由实际收尾责任人归档会话并核对结果，任务卡与会话归档分别确认。模型与推理强度按本人实际职责选择。

你可以继续使用原有产品说明、架构文档和质量规范。行业标准、专业方法和知识库都是可选内容；告诉 AI 来源与用途，由它区分参考资料与需要遵循的标准。2.0 源码候选已实现本地目录、Git revision 和 HTTPS 来源读取，实际许可、更新方式与采用条目由各项目维护。来源可读取、项目已采用和本次任务命中是三个不同事实，来源更新不会自动改变项目规则。提炼、拆分和改造文档也是可选工作；具体支持与限制见[2.0 候选说明](framework/versions/2.0.0/README.md)。

Framework 结合通用规则、项目纠正和项目长期规则开展工作。你后续明确提出的限制或撤回仍然有效。实际操作、验证和验收结果保存在项目中，便于后续核对。

2.0 源码候选包含项目自有专业文档与采用引用的联合发布实现。它分别核对正文写入和项目配置授权，普通读取不取项目协调锁，真实多对象发布与恢复保留必要写保护，并按原动作恢复中断；完整验证与独立审核仍是取得分发资格的前提，已发行版本的能力以随包说明为准。

2.0 开发中的新发行验证将源码机制与实际封存包验证分开。源码证明及独立审核形成源码资格，构包后再验证同一未改 ZIP，并由负责人成果接受。当前实现仍为 PENDING；源码资格、构包成功和分发可交付是不同结果，具体阶段见[发布流程](framework/FRAMEWORK_RELEASE.md#schema3-的源码与分发阶段)。
